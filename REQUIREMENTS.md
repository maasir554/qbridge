This is actually the design I'd pursue. I'd avoid any guest-side software or virtual camera drivers. The entire point is that **the guest OS should believe a normal USB device has been plugged into an xHCI port**.

# Project Name

**QBridge** (working name)

**Tagline**

> Native USB device bridging for QEMU over USB/IP.

---

# Objective

Create a QEMU backend that consumes USB/IP devices and injects them into QEMU's existing USB subsystem so the guest sees a **standard USB device**.

The guest must not know:

* USB/IP exists
* a network is involved
* the host is Windows
* the device is remote

# Core Principle

Do **not** emulate a webcam.

Do **not** emulate video.

Instead:

> Forward USB transactions.

Every USB request generated by Windows inside the VM is forwarded to the real webcam.

# Why integrate with QEMU instead of creating another application?

Because QEMU already has everything we need:

* USB scheduler
* xHCI emulation
* PCI bus
* hotplug support
* Windows compatibility
* USB packet routing

We're only replacing the *source* of USB packets.

Instead of:

```text
Guest ↔ QEMU ↔ libusb ↔ Physical USB
```

we build:

```text
Guest ↔ QEMU ↔ USB/IP ↔ Physical USB
```

The guest side is completely unchanged.

## One enhancement I'd add

Rather than hard-coding USB/IP, I'd make it a **generic USB transport layer**.

```
                    USB Device
                         ▲
                         │
              Transport Interface
                         ▲
     ┌───────────────────┼────────────────────┐
     │                   │                    │
     ▼                   ▼                    ▼
  libusb            USB/IP Client        Future Backends
 (local host)       (network/localhost)  (SPICE, TCP, etc.)
```

The QEMU USB device code would talk only to a transport interface:

```cpp
class USBTransport {
public:
    virtual attach() = 0;
    virtual submit_control() = 0;
    virtual submit_bulk() = 0;
    virtual submit_interrupt() = 0;
    virtual submit_isochronous() = 0;
    virtual detach() = 0;
};
```

That separation keeps the design extensible: today's backend is USB/IP, but the same architecture could support local libusb, SPICE USB redirection, or another transport in the future without changing the virtual USB device implementation. I think that modularity would make the project much more useful as an upstream-quality contribution rather than a one-off webcam bridge.
